# ReAuthz

## Языки

[English](../README.md) · **Русский** · [简体中文](README.zh-CN.md)

ReAuthz — платформа авторизации между сервисами со стандартным способом спросить, какие бизнес-
сущности доступны пользователю.

Главная решаемая проблема — дублирование контрактов и экспортов прав. Сервису не должен требоваться
отдельный endpoint для каждого потребителя, которому нужно узнать доступ пользователя к проектам,
обращениям, документам или другим ресурсам. ReAuthz даёт общий контракт такого запроса и возвращает
представление прав, которое другая система применяет к своим данным.

## Проблема

Бизнес-сущность часто принадлежит одному сервису, но используется несколькими другими.

Например:

- Сервис A владеет проектами.
- MCP-сервис, поиск или отчётная система должны показывать только доступные текущему пользователю
  проекты.
- Сервис приватных данных должен фильтровать строки базы так, чтобы каждый запрос возвращал только
  разрешённые ID сущностей.
- Система поддержки может разрешать человеку создавать обращения только от своего имени, а
  участникам команды — видеть обращения любого члена команды.

Без общего контракта каждый потребляющий сервис вынужден реализовывать собственный endpoint прав,
формат экспорта, синхронизацию и трактовку правил. Реализации расходятся: одна система показывает
проект, который другая скрывает, а одинаковая логика пользователей, групп и общих ресурсов
повторяется во многих местах.

Главный вопрос:

> Как любой системе спросить доступ этого же пользователя к тем же бизнес-сущностям, не создавая
> отдельную интеграцию прав для каждой пары сервисов?

## Стандартизированный контракт видимости

Потребляющий сервис спрашивает у ReAuthz права текущего субъекта в зарегистрированном сервисе:

    GET /service/{service_id}/permission
    Authorization: Bearer <user-token>

Концептуально ответ выглядит так:

    {
      "project": {
        "type": "sync",
        "resources": [
          { "id": "1", "name": "Project 1", "access": ["read"] },
          { "id": "2", "name": "Project 2", "access": ["read", "write"] }
        ]
      }
    }

Фактический ответ также описывает типы без конкретных ресурсов. Для них возвращается доступ ко
всему типу — это подходит для глобальных возможностей, функций, операций или режимов без ID строки.

Такой контракт даёт всем потребляющим системам одинаковый ответ на вопрос:

> «Привет, к каким сущностям этого сервиса у пользователя есть доступ?»

Потребитель использует полученные ID в своём API, интерфейсе, MCP-инструменте, поисковом запросе
или фильтре базы. ReAuthz не возвращает бизнес-записи и не забирает CRUD.

## Как публикуются ресурсы

Сервис-владелец сам отвечает за то, какие бизнес-сущности публикуются как ресурсы авторизации и
какие связи или метаданные они предоставляют.

ReAuthz может читать опубликованное представление ресурсов через:

- read-only SQL view для сервисной учётки, в том числе в реплике базы;
- HTTP endpoint ресурсов;
- синхронизатор, поддерживающий общий каталог ресурсов в актуальном состоянии.

Поэтому каждому потребителю не нужен собственный экспорт прав. Сервис сохраняет бизнес-логику и
владение данными, а ReAuthz стандартизирует контракт прав для всех потребителей.

Общие ресурсы и связи между ними также можно синхронизировать один раз и использовать в нескольких
сервисах. Это помогает сохранять одинаковую видимость, когда проект, организация, команда или
клиент появляются в разных системах.

## Какую проблему решает ReAuthz

ReAuthz строит общее представление прав поверх ресурсов, которые остаются у сервисов-владельцев:

- **Единый контракт видимости.** Потребителям не нужны отдельные endpoint вроде «мои проекты» или
  «экспорт прав» для каждой системы.
- **Точные ID ресурсов.** Ответ может содержать все доступные субъекту сущности и уровни доступа
  к каждой из них.
- **Одинаковая видимость между сервисами.** MCP, поиск, UI, отчёты, support и приватные данные
  используют один результат.
- **Удобство для базы данных.** Приложение может использовать ID в WHERE-фильтре или построить по
  ним политику row-level security (RLS).
- **Бизнес-логика остаётся у владельца.** Исходный сервис решает, какие ресурсы и связи публиковать,
  а ReAuthz вычисляет доступ к ним.
- **Меньше повторной интеграции.** Потребителям не нужны отдельные контракты, экспорты и
  синхронизации для каждого upstream-сервиса.

## Точечные проверки прав

Иногда сервису нужен не полный список видимости, а один ответ:

- может ли субъект выполнить write над проектом 42;
- может ли пользователь создать новое обращение;
- может ли член команды прочитать этот диалог.

Check API принимает несколько вопросов за один запрос и может объяснить результат: какие правила дали
доступ, какие запреты применились и какие более узкие исключения их сняли.

## Группы, роли, иерархии и правила

Главная ценность — общий контракт ресурсов и прав. Группы, роли и остальные возможности политики делают этот
контракт удобным и понятным:

- **Группы** объединяют людей. Группа — самостоятельный subject, группы можно вкладывать друг в друга, а членство
  может зависеть от claims: отдела, региона или организации.
- **Роли** — именованные наборы прав. Роль отвечает на вопрос «что можно делать» (уровни доступа на тип ресурса, на
  ресурс или на ресурс, найденный по claim), а группа — на вопрос «кто». Правило назначения выдаёт роль пользователю,
  группе или всем, кто подходит под claims, поэтому одну роль можно переиспользовать.
- **Иерархия типов ресурсов** может ссылаться на родителя из того же или другого сервиса: право на родителя
  каскадом раскрывается в ресурсы ниже него, в том числе в других сервисах.
- **Разрешения, запреты и узкие исключения** покрывают обычные и редкие бизнес-кейсы.
- **Даты начала и окончания** позволяют выдавать временный доступ.
- **Права на тип целиком** покрывают возможности без конкретного ID ресурса.

Например, сервис проектов публикует проекты, сервис команд — состав команд, а сервис поддержки — обращения. Роль
«агент поддержки» даёт право читать обращения, а правило назначения выдаёт её группе «Команда поддержки»: каждый новый
участник группы сразу получает доступ. Потребителям не нужно изобретать разные протоколы прав.

## Чем ReAuthz не является

- Это не identity provider. ReAuthz использует токены OAuth2/OIDC и их claims.
- Это не бизнес-база данных. Исходные сервисы сохраняют записи и отвечают за CRUD.
- Это не расширение RLS базы. ReAuthz возвращает разрешённые ID или решения, а потребляющий сервис
  сам применяет их к своим запросам и слою хранения.
- Это не только фильтр frontend. Backend и слой работы с данными должны принудительно применять
  результат.

## Попробовать

В репозитории есть PostgreSQL, Redis, локальный Dex OIDC, среда выполнения (core), административный API (admin-api) и административный интерфейс (web):

    task dev

Откройте http://localhost:3000 и используйте admin@example.com / password. Эти данные предназначены
только для разработки.
